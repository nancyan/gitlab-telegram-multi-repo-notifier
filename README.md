# GitLab Telegram Multi-Repo Notifier

A self-hosted Telegram notifier for one or many GitLab projects. It can send
project events to shared Telegram chats and private notifications to individual
users.

It does **not** require access to the GitLab server. Project Maintainer or Owner
permissions are normally enough to create a project webhook.

## Features

- Multiple GitLab projects, each with its own webhook URL and secret token.
- Optional shared Telegram chat per project.
- Private notification when a user is assigned to an issue or merge request.
- Private notification when a user is added as a merge request reviewer.
- Private notification for `@username` mentions in comments.
- Push, tag, issue, merge request, comment, pipeline, job, and release events.
- Telegram long polling by default, so Telegram does not need to connect to the
  server.
- Optional Telegram webhook mode.
- Optional SOCKS5 proxy for all outgoing Telegram Bot API requests.
- SQLite storage, delivery deduplication, Docker Compose deployment, and no
  GitLab API token requirement.

## How it works

GitLab sends an HTTPS webhook to this service. The service validates the
project-specific secret, creates the message, and sends it to Telegram. For a
private notification, the GitLab username must first be linked to a Telegram
account with a single-use code generated by an administrator.

## Requirements

- A Linux server with Docker and Docker Compose.
- A public HTTPS domain that points to the server.
- A reverse proxy such as Cloudflare Tunnel, Nginx, Caddy, or Traefik.
- A Telegram bot token from [@BotFather](https://t.me/BotFather).
- GitLab permission to create webhooks in the required projects.

Port `8000` is used by the container. Your public reverse proxy should send
`https://your-domain.example/*` to `http://127.0.0.1:8000` (or to the Docker
service name and port when both services share a Docker network). It is fine if
Xray/3x-ui already occupies public port 443, provided that your existing proxy
or Cloudflare Tunnel routes the notifier domain to port 8000.

## Installation

```bash
git clone https://github.com/nancyan/gitlab-telegram-multi-repo-notifier.git
cd gitlab-telegram-multi-repo-notifier
cp .env.example .env
nano .env
```

Set at least:

```ini
TELEGRAM_BOT_TOKEN=123456789:your_bot_token
TELEGRAM_BOT_USERNAME=your_bot_username_without_at
PUBLIC_BASE_URL=https://gitlab-bot.example.com
ADMIN_TELEGRAM_USER_IDS=123456789
```

`ADMIN_TELEGRAM_USER_IDS` contains Telegram numeric user IDs separated by
commas. You can obtain yours from a Telegram ID bot, or start the service, add
the bot to a chat, and use `/chatid` for the current chat ID.

Start the service:

```bash
docker compose up -d --build
docker compose logs -f notifier
```

Check the public endpoint:

```bash
curl https://gitlab-bot.example.com/health
```

Expected response:

```json
{"status":"ok"}
```

## Telegram access through a SOCKS5 proxy

If Telegram is blocked where the notifier is hosted, add this to `.env`:

```ini
TELEGRAM_PROXY_URL=socks5://username:password@proxy-host:1080
```

Special characters in the username or password must be URL-encoded. The proxy
must be reachable **from inside the notifier container**. If the SOCKS5 server
runs in another container, put both services on the same Docker network and use
the proxy container name as `proxy-host`.

The default mode is polling:

```ini
TELEGRAM_UPDATE_MODE=polling
```

In polling mode, Telegram never needs to make an incoming connection to the
notifier. Only the notifier makes outgoing requests to Telegram, optionally
through SOCKS5.

## Add a GitLab project

Open a chat with the bot and send:

```text
/addrepo group/project
```

The current chat becomes the shared notification chat. To create a project
with private notifications only:

```text
/addrepo group/project personal
```

To send shared notifications to a different chat:

```text
/addrepo group/project -1001234567890
```

The bot returns:

1. A unique webhook URL.
2. A secret token that is shown only once.

In GitLab open **Project → Settings → Webhooks**, paste both values, keep SSL
verification enabled, select the desired triggers, and create the webhook.
GitLab's **Test** button can be used after saving it.

The project path in `/addrepo` must match GitLab's full path with namespace,
for example `company/backend/api`.

## Link a GitLab user to Telegram

An administrator sends:

```text
/linkcode @gitlab_username
```

The bot returns a single-use Telegram link. Send it privately to that user.
When the user opens it and presses **Start**, their GitLab username is linked to
their private Telegram chat.

The optional GitLab numeric user ID makes matching more robust:

```text
/linkcode @gitlab_username 42
```

No GitLab API key is required. The username and optional user ID come from the
GitLab profile or webhook payload.

## Bot commands

Administrator commands:

| Command | Purpose |
| --- | --- |
| `/addrepo group/project [CHAT_ID\|personal]` | Add a project and create webhook credentials |
| `/repos` | List configured projects, keys, chats, and events |
| `/repoevents KEY issue,note,merge_request` | Change enabled event types |
| `/disablerepo KEY` | Temporarily disable a project webhook |
| `/enablerepo KEY` | Enable it again |
| `/linkcode @username [USER_ID]` | Create a private-account linking code |

User commands:

| Command | Purpose |
| --- | --- |
| `/status` | Show the linked GitLab username and notification state |
| `/stop` | Disable private notifications |
| `/start` | Re-enable private notifications |
| `/chatid` | Show the current Telegram chat ID |

Supported event names for `/repoevents` are `issue`, `job`, `merge_request`,
`note`, `pipeline`, `push`, `release`, and `tag_push`.

## Telegram webhook mode (optional)

Polling is recommended for restricted networks. If Telegram can reach the
public domain, webhook mode is also available:

```ini
TELEGRAM_UPDATE_MODE=webhook
TELEGRAM_WEBHOOK_SECRET=a-long-random-secret-at-least-16-characters
```

The bot configures `PUBLIC_BASE_URL/webhooks/telegram` automatically at startup.

## Update

```bash
git pull
docker compose up -d --build
docker compose logs -f notifier
```

The named Docker volume `notifier-data` keeps repositories, user links, and
delivery history across container rebuilds.

## Troubleshooting

View logs:

```bash
docker compose logs --tail=200 notifier
```

Common causes:

- `401 Invalid webhook secret`: GitLab's **Secret token** does not match the
  value returned by `/addrepo`.
- `404 Repository not found`: the URL key is incorrect or the project has been
  disabled.
- Project mismatch in logs: `/addrepo` used a path different from GitLab's
  `path_with_namespace`.
- Shared message arrives but private message does not: create a `/linkcode` for
  the exact GitLab username and let the user open it in a private Telegram chat.
- Telegram polling errors: check the SOCKS5 address and confirm the proxy is
  reachable from the container.
- GitLab cannot deliver the webhook: confirm that the public URL has a valid
  HTTPS certificate and routes to port 8000.

## Security

- GitLab webhook secrets are stored as SHA-256 hashes, not plaintext.
- Linking codes are single-use and expire after 60 minutes by default.
- Keep `.env` private and never commit it.
- Use HTTPS and leave GitLab SSL verification enabled.
- Limit `ADMIN_TELEGRAM_USER_IDS` to trusted accounts.
